fix: verify 认不出「启动器与实际进程不同」，LM Studio 被误判没在跑

实测事故（2026-11-09）：LM Studio 启动入口是
  resources\app\.webpack\lms.exe（CLI 启动器，拉起 GUI 后自己就退出）
真正在跑的是 F:\program\LM Studio\LM Studio.exe（5 个 Electron 进程）。
findResidualProcesses 只按 lms.exe 这个名字取候选进程，拿到空数组，
循环一次都不进 → 端口占用者的认领逻辑永远没机会跑。结果：
  端口 1234 在监听 + 探针返回 200，却判「没有相关进程存活」→ verdict fail

修复：
- 候选集加入端口占用者，不再依赖"按启动入口名字能查到进程"
- 认领口径扩充为四条：同名 exe / 端口占用者 / 同程序目录 / 已认领进程的后代
- 程序目录改为「目录链」并能识别程序根：遇到 resources、app、bin、
  node_modules、.webpack 这类容器型目录名才继续上溯，普通名字即停。
  不能退到盘符根——否则 C:\Apps\x.exe 会把整块 C 盘的进程都认成同一个
  程序（测试里 C:\Other\unrelated.exe 当场被误认，已加用例守住）
- 两遍扫描：先取直接证据再沿父链延伸，避免结果依赖遍历顺序
- 顺带修文案：期望停止时"不可达"是正常结果，原先把 ✓ 和"不可达（fetch
  failed）"摆在一起读着互相矛盾，现在明确标注"应当不可达：正常"

新增 3 条回归测试（启动器同名/同目录/无关进程不误报），119 项全绿。
